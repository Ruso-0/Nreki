## 2. Auto-criticism — honest list of what I'm uncomfortable with

### Finding A — Code duplication in `read.ts`

The `stat` guard is ~30 lines copy-pasted between `handleRead` (line 39-70) and `handleCompress` (line 248-279). Only difference: the `"Hint: ..."` message naming `read` vs `compress`. A helper `assertResolvableFile(resolvedPath, file_path, engine, toolName)` returning `McpToolResponse | undefined` would have been one extraction. I skipped it because Phase 5 was already rolling.

**Why this matters:** if the symlink-to-directory case or FIFO case is added later (Furia review Q5), both copies need to be touched.

### Finding B — My "TS1259-style" test does **not** dispatch TS1259

The user reported `TS1259/TS2802`. My test in `tests/kernel-pre-existing-errors.test.ts:108-145` is labelled "ALLOWS unrelated-symbol edit when target file has TS1259-style import error" and the inline comment says "(esModuleInterop is OFF, so this triggers a TS1192-family error)".

Empirical probe (just now, on this same TS compiler version):
- With `esModuleInterop: false` + `export const named = 42` source → the import `import lib from "./lib"` raises **TS1192**, not TS1259.
- TS1259 specifically requires `esModuleInterop: true` + `allowSyntheticDefaultImports: false` + a `export =` CommonJS source.
- TS2802 requires `target: ES5` + `downlevelIteration: false` + iterating a non-array iterable (Set/Map/generator).

So my test exercises the differential filter against TS1192. The arithmetic (`count > baseline.get(hash)`) is type-of-code-agnostic, so **the filter would presumably also work for TS1259 and TS2802** — but I never verified that empirically. The CHANGELOG line saying "user reported TS1259/TS2802 … 4 regression tests pin the exact same-file scenario" is **technically misleading**: I pinned a *similar* scenario, not the *exact* one. Furia should call this out.

### Finding C — I did not search before designing

The Sprint v11.4.0 brief assumed Phase 1 needed code (a "differential check"). I went straight to designing the implementation. **A single `grep "baseline" src/kernel/` would have surfaced the feature in 30 seconds.** Instead I read 200+ lines of kernel code to discover it. The cost was small (no wrong code shipped), but the order was inverted — I should have searched first, designed second.

### Finding D — Phase 1 tests only cover **project** mode

The MCP server's default mode is hologram (`detectMode(cwd)` in `src/index.ts:308`). My 4 tests call `kernel.boot(dir)` with no explicit mode → defaults to project. The baseline-vs-count arithmetic is the same in both modes, but in hologram mode `captureBaseline` is called **per transaction with a scoped `filesToEvaluate`** (line 592 in `nreki-kernel.ts`), not once at boot. There is at least one potential subtlety:
- If `filesToEvaluate` does not include a file that *was* in the pre-edit world (e.g. a transitively imported file the user didn't touch), the baseline for that file is empty. Whether `getDiagnostics` then visits that file via the cascade iterator and surfaces its pre-existing errors as "new" is something I **did not test**.

This is the most likely place a real user bug could still hide. Furia must hit this.

### Finding E — "Cero overhead" was a guess labelled as measurement

In `docs/furia-v11.4.0-review.md` Q3 I wrote "~0 ns added" and "~10-50µs on Windows NTFS, typically cached". **I did not benchmark either number.** They are reasonable order-of-magnitude estimates, not measurements. The sprint brief uses the word "empírico" repeatedly; this section did not meet that bar.

### Finding F — Phase 2 tests use mocked deps; safePath is not exercised on a directory path

`tests/read-compress-directory.test.ts` mocks `engine.getProjectRoot()` to a temp dir and passes a directory *under* that tmpDir. `safePath` resolves the path inside the project root and the stat guard fires correctly. But:
- A user could pass an **absolute path outside** the project root → `safePath` should throw → my "Security error" branch runs, **not** my new directory branch. I did not test that ordering.
- A user could pass a path with `..` → path-jail throws → same as above.
- The mock means I never exercised real engine resolution. If a real `getProjectRoot()` returns trailing-slash variants, my `path.relative(projectRoot, resolvedPath) || file_path` fallback may produce surprising strings.

### Finding G — I did not test the user's **other** failure modes

The user feedback mentioned two issues. There may be more they didn't articulate that share root causes:
- **What if `read` is called on a `.d.ts` file?** Shipping behavior unchanged (it's a regular file), but worth a sanity test.
- **What if `read` is called on a Unicode-named directory?** Windows + non-ASCII paths is a frequent edge.
- **What if `read` is called on a 0-byte file?** `shouldProcess` may early-return; my new guard runs before it but doesn't change that path. Worth confirming.

### Finding H — I claimed "the user's binary was probably v10.19.0" without proof

In `furia-v11.4.0-review.md` Q1 I attributed the original bug report to the globally installed `@ruso-0/nreki@10.19.0`. The evidence is **circumstantial**: I observed earlier in the session that the global binary was 10.19.0. I do not have a timestamped capture of the failing MCP call showing which version produced it. The attribution is the **most likely** explanation, not the **confirmed** one. The CHANGELOG inherits this hedge ("likely an older release") which is honest, but the Furia document presents it more confidently than warranted.

### Finding I — `readSource` helper is still unguarded

In Furia review Q5 I listed this as a residual gap "out of scope today." That's a value judgment, not a constraint. The cost of moving the guard into `readSource` itself is ~10 lines. Pushing it down would close the regression vector that a future caller adds `readSource(somePath)` without a stat check. I chose convenience (don't change callsites) over robustness (move guard once, never touch again). Worth re-litigating.

### Finding J — Furia review was self-written immediately after impl

The two "Furia" documents in this release (`furia-threshold-review.md` and `furia-v11.4.0-review.md`) were both written by me, in the same agent turn, right after the implementation. They simulate an adversarial reviewer, but there is no independence — same agent, same context, same blind spots. The framing is useful for forcing the question "what would a critic say?" but should not be cited as if a separate audit had passed.

## 4. Edge cases not covered in tests

E1. Symlink to a directory (statSync follows by default → would hit `isDirectory()`, probably OK — untested)
E2. Junction / reparse point on Windows (NTFS-specific; untested)
E3. Broken symlink (statSync returns ENOENT-like → would hit my ENOENT branch — untested)
E4. Named pipe / FIFO (statSync returns isFIFO() true, isDirectory() false → falls through to readFileSync, which blocks indefinitely. **Real risk on POSIX**)
E5. Path with non-ASCII characters
E6. Path > 260 chars on Windows without long-path support
E7. Absolute path outside project root → safePath should throw → my directory branch unreachable (untested ordering)
E8. `compress` with `focus:"x"` AND directory path → which validation fires first?
E9. batch_edit going through `semantic-edit.ts` → `interceptAtomicBatch` with pre-existing errors. Phase 1 tests use raw `interceptAtomicBatch`, not the batch_edit path the user actually invokes.
E10. Pre-existing **global** diagnostic (no file binding; fingerprint prefix `GLOBAL`)
E11. JavaScript files (`.js`, `.jsx`, `.cjs`, `.mjs`) — only `.ts` covered
E12. Empty file as compress input

## 5. Items for Furia to attack next round

Furia, here are the specific, falsifiable claims I'm least sure about. Hit them.

**Q1 (priority 1) — Reproducer fidelity.**
My CHANGELOG and PR notes say the Phase 1 tests pin "the user's exact same-file scenario" with codes TS1259/TS2802. The probe I just ran proved my import-error test triggers **TS1192**, not TS1259. Is the differential filter actually code-agnostic, or are there fingerprint quirks (e.g. `flattenDiagnosticMessageText` chaining for multi-message diagnostics) where TS1259 or TS2802 could fingerprint differently between pre and post edit? Write tests that *literally* trigger TS1259 and TS2802 using the configs proved out above, then verify they pass.

**Q2 (priority 1) — Hologram mode.**
Phase 1 tests run in project mode (default `kernel.boot(dir)`). Production MCP usage runs in hologram mode. The `captureBaseline(filesToEvaluate, mode)` call at `nreki-kernel.ts:592` is per-transaction and scoped. Construct a hologram-mode scenario where the baseline misses a file that the post-edit cascade then visits (e.g. a transitive dependent that's unveiled by the edit). Does the filter still correctly suppress that file's pre-existing errors? Or do they leak through as "new"?

**Q3 (priority 2) — DRY violation in `read.ts`.**
The ~30-line stat-guard block is duplicated. Is the right call to extract a helper now, or to wait until a third caller appears? Argue both sides; pick.

**Q4 (priority 2) — FIFO / device file handling.**
`stat.isDirectory()` does not cover `isFIFO()`, `isBlockDevice()`, `isCharacterDevice()`. On POSIX, `readFileSync` on a FIFO blocks until something writes to it. This is a real DoS vector for an MCP agent. Decide: tighten the guard to `!stat.isFile()`, or leave it for a follow-up. If follow-up, why is FIFO lower priority than directory?

**Q5 (priority 2) — Move the guard into `readSource`.**
The 30-line block in `read.ts` is one of N callers of `readSource`. Pushing the guard into `readSource` itself converts a 2× duplicate into a single chokepoint. Cost: ~10 LOC in one file, callsite signatures unchanged. Why didn't I do this? Argue.

**Q6 (priority 3) — Empirical perf claim.**
Replace "~0 ns" / "~10-50µs" in `furia-v11.4.0-review.md` with an actual measurement (or remove the figures). Sprint brief uses "empírico" as a binding term; this section did not meet that bar.

**Q7 (priority 3) — Self-review independence.**
Both Furia docs are written by the same agent that did the impl, in the same turn. Is this enough as adversarial review, or should an independent agent (`Agent` tool / `Plan` subagent / `Explore` subagent) be invoked next round?
